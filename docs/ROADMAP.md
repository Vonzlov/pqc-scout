# План разработки pqc-scout

Этот документ описывает, что мы строим, где проходят границы проекта и в каком порядке идём. Границы фиксируются здесь один раз: всё, что в них не попало, перечислено в разделе «Вне рамок» и в этот проект не возвращается. Незнакомые термины объяснены в [глоссарии](GLOSSARY.md).

## Что строим

pqc-scout — инструмент командной строки, который проходит по Python-репозиторию и находит квантово-уязвимую асимметричную криптографию: RSA, эллиптические кривые, классический Диффи — Хеллман. Для каждой находки он оценивает, насколько срочно её нужно мигрировать, и предлагает замену на постквантовые алгоритмы ML-KEM и ML-DSA. На выходе получаются два результата: криптографическая инвентаризация в формате CycloneDX CBOM для машин и отчёт с объяснениями, приоритетами и патчами для человека.

Проект делится на две части разной природы. **Детектор** детерминированный: он ищет криптографию по правилам и не использует LLM, поэтому его качество можно точно измерить и проверять в CI на каждом коммите. **Аналитик** — LLM-агент. Он берёт каждую находку и изучает окружающий код, чтобы понять, что именно защищает ключ. Затем сверяется с базой знаний по стандартам NIST, пишет оценку риска и рекомендацию, а где возможно, генерирует патч и проверяет его тестами. Это разделение — главный архитектурный принцип проекта: всё, что можно сделать правилами, делается правилами, а модель отвечает только за то, что требует понимания контекста.

Обе части собраны в один граф на LangGraph. Детектор в нём — обычный узел без LLM, а аналитик — несколько узлов с циклом и точкой, где решает человек.

Момент для проекта удачный. С версии 48 библиотека `cryptography` (pyca), через которую идёт почти вся криптография в Python, поддерживает ML-KEM и ML-DSA, а с версии 49 ещё и сертификаты X.509 с ключами ML-DSA. Значит, патчи можно предлагать в рамках той же библиотеки, которую код уже использует, без экзотических зависимостей.

## Границы MVP

Детектор ищет две вещи. Первая — вызовы трёх библиотек в Python-коде: `cryptography` (pyca), `pycryptodome` и `PyJWT`. Это генерация и загрузка ключей RSA, DSA, DH, EC, Ed25519/Ed448 и X25519/X448, шифрование RSA-OAEP, создание и проверка подписей, асимметричные алгоритмы JWT (RS*, PS*, ES*, EdDSA). Вторая — файлы ключей и сертификатов в самом репозитории (PEM, DER, открытые ключи OpenSSH): у каждого определяются алгоритм и длина ключа.

Аналитик для каждой находки определяет назначение: конфиденциальность, подлинность или тестовый код. Если код даёт для этого основания, он оценивает, как долго защищаемые данные должны оставаться секретными. Дальше он присваивает приоритет по модели риска (см. ниже) и пишет рекомендацию со ссылками на стандарты и на конкретные строки кода. Патч в формате diff предлагается только для кода на `cryptography`; для `pycryptodome` и `PyJWT` будет только текстовая рекомендация. Патч применяется к рабочей копии только после явного подтверждения человеком; без подтверждения код не меняется.

## Вне рамок

В проект не входят: другие языки программирования; конфигурационные файлы nginx, sshd и OpenSSL; сканирование живых TLS-эндпоинтов; криптография внутри установленных зависимостей; применение патчей без подтверждения человека; параллельная обработка находок; веб-интерфейс и API-сервис; симметричная криптография; квантовые схемы на симуляторе (Шор, BB84). Последнее — отдельная учебная история, её место в курсовой, а не здесь.

## Архитектура

Анализ — это граф LangGraph с общим состоянием. Находки обрабатываются по одной: узел `pick` берёт следующую, а когда они заканчиваются, граф уходит в отчёт.

```
 Python-репозиторий
         │
         ▼
       scan ──► findings.json, cbom.json
         │
         ▼
       pick ◄───────────────────────────────┐
         │  находок нет ──► report          │
         ▼                                  │
      assess ── патч не нужен ─────────────►┤
         │                                  │
         ▼                                  │
       patch ◄──┐                           │
         │      │ тесты упали,              │
         ▼      │ попыток < 3               │
      verify ───┘                           │
         │ ── три неудачи ─────────────────►┤
         ▼                                  │
      review ──────────────────────────────►┘
```

| Узел | Что делает | LLM |
|---|---|---|
| `scan` | детектор: находит уязвимую криптографию по правилам, пишет `findings.json` и `cbom.json` | нет |
| `pick` | берёт следующую необработанную находку или отправляет граф в `report` | нет |
| `assess` | собирает контекст из кода, ищет по базе знаний, определяет назначение и приоритет, пишет рекомендацию с обоснованиями | да |
| `patch` | генерирует unified diff; при повторной попытке получает текст ошибки из `verify` | да |
| `verify` | применяет патч к временной копии, проверяет, что файл парсится, прогоняет тесты | нет |
| `review` | останавливает граф через `interrupt()` и ждёт решения человека: применить патч или отклонить | нет |
| `report` | собирает `report.md` и патчи | нет |

LangGraph здесь оправдан тремя вещами: циклом «патч → тесты → исправление» с выходом по лимиту, паузой до решения человека и длинными прогонами по большому репозиторию, которые должны переживать перезапуск. Если бы аналитик только читал код и писал рекомендацию, хватило бы обычного цикла с вызовом модели, и граф был бы лишним. После неудачной третьей попытки патч помечается как непроверенный, и находка попадает в отчёт без него.

Состояние графа после каждого шага сохраняет SQLite-чекпоинтер. Прогон, прерванный посреди находок, продолжается с того же места по `thread_id`, а ответ человека в `review` передаётся через `Command(resume=...)`.

У инструмента три команды: `pqc-scout scan <путь>` вызывает детектор напрямую, без графа и модели, и пишет `findings.json` и `cbom.json`; `pqc-scout analyze <путь>` запускает граф целиком и пишет отчёт, а с флагом `--resume <thread_id>` продолжает прерванный прогон; `pqc-scout eval` прогоняет оценку качества на эталонном наборе.

## Модель риска

Приоритет зависит от двух вопросов: что защищает криптография и сколько это должно оставаться защищённым. Логика опирается на угрозу «собери сейчас, расшифруй потом» и неравенство Моски (оба понятия есть в глоссарии).

**P1, критично.** Ключ обеспечивает конфиденциальность (обмен ключами, шифрование) данных, которые должны оставаться секретными годами. Такие данные можно перехватить и сохранить уже сегодня, поэтому угроза актуальна сейчас, а не после появления квантового компьютера.

**P2, высокий.** Долгоживущие подписи: подпись кода, прошивок и документов, корневые и промежуточные сертификаты. Подделать их «впрок» нельзя, но если ключ доживёт до появления квантового компьютера, им можно будет подписать что угодно.

**P3, средний.** Короткоживущая криптография: сессионные токены, эфемерная аутентификация. Мигрировать нужно, но атаковать её можно только в моменте и только при наличии квантового компьютера.

**P4, низкий.** Тесты, примеры, неиспользуемый код.

**Не определено.** Аналитику не хватило оснований для вывода. Такая находка честно уходит человеку, а не получает приоритет наугад.

Любой вывод аналитика должен опираться на обоснование: ссылку на строки кода (файл и номер строки) или на фрагмент базы знаний. Обоснования проверяются автоматически: строка должна существовать и содержать упомянутый символ, фрагмент должен быть в базе. Находка с битым обоснованием помечается в отчёте. Горизонт угрозы z из неравенства Моски задаётся в конфиге как допущение, а не прогноз; по умолчанию берём 2035 год.

## Процесс разработки и GitHub

Репозиторий — `Vonzlov/pqc-scout`, публичный. Работаем прямо в `main`: каждое законченное изменение — отдельный коммит, после которого проект собирается и тесты проходят. Перед коммитом локально запускаем `uv run ruff check` и `uv run pytest`.

Коммиты пишем на английском по Conventional Commits: `feat(detector): detect RSA key generation in pyca/cryptography`, `test(testbed): add HS256 negative case`, `docs: describe risk model`. README — на английском, документация в `docs/` и комментарии в коде — на русском, имена переменных и функций — на английском.

Завершение этапа с версией отмечается тегом (`v0.1.0` и далее).

CI на каждый пуш запускает ruff, pytest, а с этапа 3 ещё и оценку детектора на эталонном наборе с порогом качества: если полнота упала ниже порога, сборка падает. Граф тестируется на заглушках вместо моделей, поэтому тесты маршрутов тоже идут в CI. Оценку аналитика с настоящей моделью в CI не гоняем, ей нужен GPU. Её запускаем локально, а результаты коммитим в `eval/results/` с названием модели и датой.

Ключи API (GigaChat и прочие) живут только в `.env`, который прописан в `.gitignore`; в репозитории лежит `.env.example` с пустыми значениями.

Ключевые решения фиксируем короткими записями в `docs/decisions/`: контекст, рассмотренные варианты, выбор, последствия. Первые кандидаты: детектор на `ast` вместо Semgrep; LangGraph для аналитика и почему детектор остаётся обычным кодом; последовательная обработка находок вместо параллельной; SQLite-чекпоинтер вместо Postgres; поиск без векторной БД; версия CycloneDX.

## Этапы

Оценки сроков даны из расчёта 6–8 часов в неделю. Всё вместе займёт примерно 11–16 недель, но после этапа 4 у проекта уже есть самостоятельно полезная и показываемая часть.

### Этап 0. Каркас (≈1 неделя)

Цель — пустой, но правильно устроенный проект, в котором CI уже работает, а окружение проверено на всех машинах.

Создаём репозиторий с лицензией MIT, настраиваем uv-проект с раскладкой `src/`, ruff, pytest и GitHub Actions. Пишем smoke-тест: `cryptography>=48` импортирует модули `mlkem` и `mldsa`, делает инкапсуляцию с декапсуляцией и подпись с проверкой. Отдельно проверяем, что Ollama отвечает из того окружения, где запускается проект: на стационарном ПК проект живёт прямо в Windows, рядом с Ollama. MacBook на процессоре Intel, а начиная с `cryptography` 49 готовые сборки для macOS выпускаются только под arm64. Поэтому в `pyproject.toml` версия ограничена 48.x: ML-KEM и ML-DSA в ней уже есть, а X.509 с ML-DSA из версии 49 для MVP не нужен.

Готово, когда:
- [x] CI зелёный на пустом проекте;
- [x] smoke-тест PQC проходит локально и в CI;
- [x] Ollama доступна из рабочего окружения.

### Этап 1. Скелет графа на заглушках (≈1 неделя)

Цель — разобраться в механике LangGraph до того, как в проекте появятся модели и настоящий детектор. Все узлы — заглушки с фиксированными значениями: `scan` отдаёт три захардкоженные находки, `assess` берёт приоритеты из словаря, `verify` проваливает первые две попытки и проходит на третьей. Так видно, как течёт состояние и как работают рёбра, без шума от моделей.

Должно заработать: типизированное состояние и редьюсеры для полей, которые накапливаются по ходу прогона; условные рёбра после `pick`, `assess` и `verify`; цикл `patch → verify` с выходом по счётчику попыток; `interrupt()` в узле `review` с продолжением через `Command(resume=...)`; SQLite-чекпоинтер, благодаря которому прогон, прерванный посреди находок, продолжается по `thread_id`. Команда `pqc-scout analyze` на этом этапе гоняет граф на заглушках и в узле `review` спрашивает в терминале, применять ли патч.

Узлы — обычные функции, поэтому каждый проверяется тестом отдельно. Граф целиком прогоняется на заглушках, и тест проверяет маршрут: какие узлы пройдены и в каком порядке, и что после трёх неудач находка уходит в отчёт без патча.

Готово, когда:
- [ ] граф на заглушках проходит все ветки, включая повтор и выход по лимиту;
- [ ] прерванный прогон продолжается с места остановки;
- [ ] `review` останавливает граф и продолжает его по ответу человека;
- [ ] тесты маршрутов зелёные в CI;
- [ ] схема графа из `draw_mermaid()` добавлена в README.

### Этап 2. Предметная подготовка и разметка (1–2 недели)

Цель — разобраться в предмете настолько, чтобы уметь вручную размечать примеры, и собрать данные, по которым потом будем мерить качество. Этап выглядит скучным, но именно он отличает проект с измеренным качеством от демо, которое работает «на глаз».

Начинаем с глоссария, затем читаем введения к FIPS 203 и 204 и документацию `cryptography` по `mlkem` и `mldsa`. Параллельно собираем эталонный набор (testbed) из 40–60 маленьких примеров. Каждый пример — папка с кодом и файлом `expected.yaml`, в котором перечислены ожидаемые находки: файл, строка, алгоритм, операция, назначение, приоритет. Обязательно включаем ловушки, на которых детектор не должен срабатывать: HS256 в JWT (это симметричный HMAC), переменную с именем `rsa`, не связанную с криптографией, упоминание RSA в комментарии или строке, SHA-256 и AES-GCM. Часть примеров снабжаем маленьким тестом вроде «зашифровать и расшифровать» или «подписать и проверить», чтобы на этапе 6 проверять патчи прогоном.

Выбираем три open-source репозитория с реальной криптографией, фиксируем коммиты и размечаем находки вручную.

Пишем `docs/migration-patterns.md` — справочник эталонных замен: RSA-OAEP на ML-KEM с HKDF и AES-GCM, ECDH и X25519 на гибрид X25519 + ML-KEM-768, подписи RSA, ECDSA и Ed25519 на ML-DSA-65. У каждого паттерна должен быть работающий сниппет с тестом. Отдельно выясняем, как обстоят дела с постквантовыми алгоритмами в JWT/JOSE: насколько известно, их стандартизация в IETF ещё идёт. Справочник войдёт в базу знаний аналитика, поэтому всё в нём проверяем руками.

Пишем `scripts/fetch_kb.py`: он скачивает документы базы знаний по URL и сверяет SHA-256. PDF в репозиторий не коммитим.

Готово, когда:
- [ ] testbed содержит не меньше 40 размеченных примеров, включая ловушки;
- [ ] три реальных репозитория размечены;
- [ ] эталонные сниппеты миграции проходят тесты;
- [ ] `fetch_kb.py` скачивает и проверяет документы.

### Этап 3. Детектор (≈2 недели) → `v0.1.0`

Цель — детерминированный детектор с измеренным качеством. Он заменяет заглушку в узле `scan`.

Описываем модель `Finding` в pydantic. Пишем обход AST с разрешением импортов и алиасов: `from cryptography.hazmat.primitives.asymmetric import rsa as r` и затем `r.generate_private_key(...)` должно находиться. Правила храним в обычном Python-списке словарей «модуль, имя, алгоритм, операция», без хитрых эвристик, чтобы любой мог прочитать и дополнить таблицу. Отдельный модуль разбирает файлы ключей и сертификатов. Команда `pqc-scout scan` пишет `findings.json`.

Скрипт оценки считает precision, recall и F1 на testbed и на размеченных репозиториях, в разбивке по библиотекам и алгоритмам. В CI добавляем порог, например полнота не ниже 0.95 на testbed.

Готово, когда:
- [ ] `pqc-scout scan` работает на testbed и на реальных репозиториях;
- [ ] узел `scan` в графе вызывает настоящий детектор;
- [ ] метрики посчитаны и опубликованы в README;
- [ ] CI падает при просадке полноты ниже порога.

Готово, когда:

### Этап 5. База знаний и поиск (1–2 недели)

Цель — поиск, который по вопросу аналитика возвращает нужный фрагмент стандарта со ссылкой на документ и раздел.

Режем документы на фрагменты по разделам и сохраняем номер раздела и страницы, чтобы потом на них ссылаться. Считаем эмбеддинги локальной моделью через Ollama, храним их в `InMemoryVectorStore` с сохранением в файл и ищем косинусной близостью. Если чистый векторный поиск будет промахиваться на точных терминах вроде «ML-KEM-768», добавим BM25 и объединим результаты. Собираем 30 вопросов с эталонными фрагментами и меряем recall@5.

Готово, когда:
- [ ] recall@5 измерен и записан;
- [ ] каждый результат поиска содержит ссылку на документ и раздел.

### Этап 6. Аналитик (2–3 недели) → `v0.3.0`

Цель — по каждой находке получить обоснованную оценку и рекомендацию. Граф уже есть с этапа 1, теперь его узлы по одному становятся настоящими. Делаем в два шага, и порядок здесь важен.

**6а. Фиксированный конвейер.** `assess` собирает контекст правилами: функция с находкой и места, где используется переменная с ключом. Затем ищет по базе знаний и делает один вызов модели со структурированным выводом: `with_structured_output` получает pydantic-модель, и та же модель валидирует ответ. `patch` генерирует unified diff для кода на `cryptography`. `verify` применяет его к временной копии, проверяет, что файл парсится, и прогоняет тесты примера; при провале текст ошибки уходит обратно в `patch`.

**6б. Агент.** Второй вариант узла `assess`: модель сама решает, что прочитать. Внутри узла работает агент из `create_agent` с инструментами `read_file`, `grep`, `find_usages` и `search_kb` в пределах лимита шагов (скажем, 8). Журнал вызовов инструментов попадает в отчёт. Вариант выбирается конфигом, а на этапе 7 мы проверим, оправдывает ли агент себя.

Модель выбирается конфигом, одинаково для Ollama и GigaChat. Проверка обоснований из модели риска работает на этом же этапе.

Готово, когда:
- [ ] `pqc-scout analyze` выдаёт отчёт на testbed и на реальном репозитории;
- [ ] обоснования проверяются автоматически, битые помечаются;
- [ ] патчи проверяются прогоном тестов, непроверенные попадают в отчёт с пометкой;
- [ ] оба варианта `assess` работают и переключаются конфигом.

### Этап 7. Оценка качества и сравнение (1–2 недели) → `v0.4.0`

Цель — честные цифры, на которых держится весь проект.

Для аналитика меряем: точность определения назначения; точность приоритета (точное совпадение и с допуском в один уровень); долю валидных обоснований; долю патчей, прошедших тесты, и среднее число попыток до успеха. Двадцать рекомендаций проверяем вручную по рубрике «корректность, полнота, полезность».

Сравниваем конвейер и агента: даёт ли агентность прирост качества и какой ценой по времени и токенам. Если не даёт, так и пишем в README — это тоже результат. Сравниваем две-три локальные модели, которые помещаются в видеопамять RTX 3060, и GigaChat, и по данным выбираем модель по умолчанию. Здесь пригодится бенчмарк LLM из соседнего проекта.

Готово, когда:

## Риски

**Галлюцинации в патчах.** Патчи проверяются прогоном тестов, непроверенные помечаются, а в код попадает только то, что одобрил человек.

**Слабый вызов инструментов у небольших локальных моделей.** Именно поэтому конвейер идёт первым, а агент — вариант, который нужно оправдать метриками.

**Стандарты меняются.** NIST IR 8547 пока в проектной редакции, FIPS 206 ещё не вышел. В базе знаний храним версии и даты документов, а в отчёте указываем, на какую редакцию опирались.

**Лишние абстракции фреймворка.** LangChain легко затягивает в обёртки поверх обёрток. Из него берём только модели, инструменты, structured output и векторное хранилище в памяти; узлы графа остаются обычными функциями, которые читаются без знания фреймворка.

**Расползание объёма.** Правило одно: всё, что не входит в границы MVP, остаётся в разделе «Вне рамок».
